
## 一、后端开发基础

### 1. 后端的职责

后端主要负责处理业务逻辑、管理数据、提供接口，并保证系统安全、稳定和可维护。

常见职责包括：

- 接收前端或其他服务的请求
- 校验请求参数
- 执行业务逻辑
- 读写数据库
- 调用第三方服务
- 处理登录、鉴权和权限控制
- 返回统一格式的响应
- 记录日志和处理异常

### 2. API 的制定

API 是前端、后端和其他系统之间的通信约定。设计 API 时要保证清晰、稳定、易扩展。

常见设计要点：

- 使用清晰的资源路径，例如 `/users`、`/orders`
- 使用 HTTP 方法表达操作语义
- 使用统一的响应格式
- 使用统一的错误码
- 支持分页、排序和筛选
- 注意接口幂等性
- 保持接口版本兼容

常见 HTTP 方法：

- `GET`：查询资源
- `POST`：创建资源
- `PUT`：整体更新资源
- `PATCH`：局部更新资源
- `DELETE`：删除资源

统一响应示例：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

### 3. 参数校验

后端必须进行参数校验，不能只依赖前端校验。

常见校验内容：

- 必填字段是否为空
- 字符串长度是否合法
- 数字范围是否合法
- 邮箱、手机号、URL 等格式是否合法
- 枚举值是否合法
- 当前用户是否有权限操作该资源

参数校验可以避免脏数据进入系统，也可以降低安全风险。

### 4. 测试方法论

后端测试用于保证业务逻辑正确、接口稳定、系统改动不会引入明显回归。

常见测试类型：

- 单元测试：测试函数、方法或小模块
- 集成测试：测试数据库、缓存、第三方接口等组件协作
- 接口测试：测试 API 入参、返回值和状态码
- 回归测试：验证新修改没有破坏旧功能

测试重点：

- 核心业务流程
- 复杂条件分支
- 权限判断
- 数据库读写逻辑
- 异常场景

### 5. 文件处理与云存储

文件处理是后端常见功能，例如头像上传、附件上传、导入导出文件。

常见设计方式：

- 小文件可以直接通过后端上传
- 大文件适合分片上传
- 文件本体通常放对象存储
- 数据库只保存文件元信息
- 下载可以使用签名 URL 控制访问权限

文件元信息通常包括：

- 文件名
- 文件大小
- 文件类型
- 存储地址
- 上传用户
- 上传时间

### 6. Golang 后端开发

Go 常用于开发后端服务，特点是语法简洁、并发能力强、部署方便。

后端开发中需要重点掌握：

- `goroutine`：轻量级并发执行单元
- `channel`：协程之间通信
- `context`：控制超时、取消和请求链路
- `interface`：抽象能力
- `error`：显式错误处理
- `net/http`：HTTP 服务基础库

Go 后端项目常见分层：

- handler/controller：处理 HTTP 请求
- service：处理业务逻辑
- repository/dao：处理数据库访问
- model/entity：定义数据结构
- middleware：处理中间件逻辑，例如鉴权、日志、跨域

## 二、数据库基础

### 1. 数据库的作用

数据库用于持久化保存业务数据，并提供可靠的数据查询、更新和事务能力。

常见数据库类型：

- 关系型数据库：MySQL、PostgreSQL
- 缓存数据库：Redis
- 文档数据库：MongoDB
- 搜索引擎：Elasticsearch
- 向量数据库：Milvus、Qdrant、Pinecone

### 2. 关系型数据库核心概念

- 表：保存某类业务数据
- 行：一条具体记录
- 列：数据字段
- 主键：唯一标识一条记录
- 外键：建立表之间的关联
- 索引：提升查询效率
- 事务：保证一组操作要么全部成功，要么全部失败

### 3. 表结构设计

表结构设计要围绕业务实体展开。

设计时要关注：

- 字段是否完整
- 字段类型是否合适
- 主键是否稳定
- 是否需要唯一约束
- 是否需要外键或逻辑关联
- 是否需要创建索引
- 是否存在冗余字段

用户表示例：

```sql
CREATE TABLE users (
  id BIGINT PRIMARY KEY,
  username VARCHAR(64) NOT NULL UNIQUE,
  password_hash VARCHAR(255) NOT NULL,
  email VARCHAR(128),
  created_at TIMESTAMP NOT NULL,
  updated_at TIMESTAMP NOT NULL
);
```

### 4. SQL 基础

常见 SQL 操作包括增删改查。

```sql
INSERT INTO users (id, username) VALUES (1, 'alice');

SELECT id, username FROM users WHERE id = 1;

UPDATE users SET username = 'bob' WHERE id = 1;

DELETE FROM users WHERE id = 1;
```

常见查询能力：

- `WHERE`：条件过滤
- `ORDER BY`：排序
- `LIMIT`：限制返回数量
- `GROUP BY`：分组统计
- `JOIN`：多表关联

### 5. 索引

索引用于提升查询速度，本质上是数据库为字段建立的高效查找结构。

适合建索引的字段：

- 经常出现在 `WHERE` 条件中
- 经常用于排序
- 经常用于关联查询
- 区分度较高的字段

不适合滥用索引的原因：

- 索引会占用存储空间
- 写入、更新、删除时需要维护索引
- 索引过多会增加数据库负担

常见索引类型：

- 普通索引
- 唯一索引
- 联合索引
- 全文索引

### 6. 事务

事务用于保证一组数据库操作的一致性。

事务的 ACID 特性：

- 原子性：事务中的操作要么全部成功，要么全部失败
- 一致性：事务前后数据要保持合法状态
- 隔离性：并发事务之间不能互相破坏
- 持久性：事务提交后数据要永久保存

常见并发问题：

- 脏读
- 不可重复读
- 幻读

常见隔离级别：

- 读未提交
- 读已提交
- 可重复读
- 串行化

### 7. 慢查询优化

数据库性能优化常见思路：

- 避免 `SELECT *`
- 给高频查询字段建立索引
- 避免在索引字段上使用函数计算
- 减少深分页
- 使用合理的字段类型
- 拆分复杂 SQL
- 通过执行计划分析查询过程

## 三、GORM

GORM 是 Go 语言常用的 ORM 框架，用于把数据库表映射为 Go 结构体。

### 1. GORM 的作用

- 简化 CRUD 操作
- 管理模型和表之间的映射
- 支持事务
- 支持关联查询
- 支持自动迁移
- 支持钩子方法

模型示例：

```go
type User struct {
    ID           uint
    Username     string
    PasswordHash string
    Email        string
}
```

常见查询示例：

```go
var user User
db.Where("username = ?", "alice").First(&user)
```

### 2. 使用 GORM 的注意点

- 不要因为使用 ORM 就忽略 SQL 性能
- 复杂查询需要关注生成的 SQL
- 批量操作要避免逐条循环写入
- 事务要明确提交和回滚
- 关联查询要避免 N+1 查询问题

## 四、登录与鉴权

### 1. 登录

登录用于确认用户身份。常见流程：

1. 用户提交账号和密码
2. 后端校验账号是否存在
3. 后端比较密码哈希
4. 校验成功后生成登录态
5. 前端保存 Cookie 或 Token
6. 后续请求携带登录凭证

密码不能明文保存，应该使用安全哈希算法并加盐。

### 2. 鉴权

鉴权用于判断当前用户是否有权限访问某个资源或执行某个操作。

常见模型：

- RBAC：基于角色的权限控制
- ACL：基于资源的访问控制列表

常见鉴权方式：

- Session + Cookie
- JWT
- Access Token

### 3. 常见安全风险

- SQL 注入
- 越权访问
- Token 泄露
- 密码明文存储
- 暴力破解
- 重放攻击

防护方式：

- 使用参数化查询
- 后端统一鉴权
- 密码加盐哈希
- 登录失败次数限制
- Token 设置过期时间
- 敏感接口二次校验

## 五、缓存

### 1. 缓存的作用

缓存用于提高访问速度，减少数据库压力。

常见缓存场景：

- 热点数据
- 用户会话
- 配置信息
- 排行榜
- 短时间内频繁读取的数据

### 2. Redis 常见用途

- 缓存查询结果
- 保存登录态
- 分布式锁
- 计数器
- 限流
- 排行榜
- 消息队列的简单替代方案

### 3. 缓存常见问题

缓存穿透：

- 查询不存在的数据，请求持续打到数据库
- 解决方式：空值缓存、布隆过滤器

缓存击穿：

- 热点 Key 失效，大量请求同时访问数据库
- 解决方式：互斥锁、热点数据永不过期、提前刷新

缓存雪崩：

- 大量 Key 同时失效，数据库压力骤增
- 解决方式：过期时间加随机值、多级缓存、限流降级

### 4. 缓存一致性

缓存和数据库同时存在时，要考虑数据一致性。

常见策略：

- 先更新数据库，再删除缓存
- 设置合理过期时间
- 对关键业务使用消息队列同步变更
- 对强一致场景减少缓存依赖

## 六、搜索引擎与 ES

### 1. 搜索引擎的作用

搜索引擎适合处理全文搜索、复杂筛选和聚合分析。

适用场景：

- 商品搜索
- 文章搜索
- 日志检索
- 用户行为分析
- 多条件筛选

### 2. Elasticsearch 核心概念

- Index：索引，类似数据库中的表
- Document：文档，类似一条记录
- Field：字段
- Mapping：字段结构定义
- Inverted Index：倒排索引
- Analyzer：分词器

### 3. 数据同步

实际系统中，数据库通常是主数据源，ES 是搜索副本。

常见同步方式：

- 业务代码写数据库后同步写 ES
- 使用消息队列异步同步
- 监听数据库 binlog 同步

需要关注：

- 数据延迟
- 同步失败重试
- 数据一致性
- 删除和更新的处理

## 七、向量数据库

### 1. 向量数据库的作用

向量数据库用于存储向量并进行相似度检索。

常见场景：

- 语义搜索
- 推荐系统
- 图片相似搜索
- RAG 知识库检索

### 2. 核心概念

- Embedding：把文本、图片等内容转换成向量
- 相似度：衡量两个向量的接近程度
- TopK：返回最相似的前 K 条结果
- ANN：近似最近邻搜索，用于提升检索性能

### 3. 后端接入流程

1. 原始数据入库
2. 调用模型生成 embedding
3. 将向量和元数据写入向量数据库
4. 用户查询时生成查询向量
5. 在向量数据库中检索相似内容
6. 返回结果或进入后续业务流程

## 八、实时通信技术

### 1. 常见方式

- WebSocket：适合双向实时通信
- SSE：适合服务端持续向客户端推送

### 2. 适用场景

- 聊天系统
- 实时通知
- 协同编辑
- 订单状态推送
- 在线状态同步

### 3. 后端关注点

- 连接管理
- 用户身份校验
- 消息路由
- 断线重连
- 心跳检测
- 消息可靠性

## 九、支付后端：Stripe

Stripe 属于后端常见的第三方支付集成能力。

后端接入重点：

- 创建支付会话
- 接收 Webhook 回调
- 校验回调签名
- 处理支付成功、失败、退款等状态
- 保证订单状态幂等更新
- 做好对账和异常补偿

支付系统必须重视幂等性。相同支付事件可能被重复通知，后端不能重复发货或重复入账。
