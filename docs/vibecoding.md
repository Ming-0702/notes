# Vibe Coding 笔记

Vibe Coding 不是“让 AI 替我写完所有代码”，而是一种更快的创作方式：人负责方向、判断和验收，AI 负责把想法快速展开成可运行的草稿。

它适合从零开始做原型、写脚本、搭建小工具、整理已有代码、补测试、改交互细节。它不适合完全放弃理解，也不适合把没有验证过的代码直接丢进生产环境。

## 核心感觉

传统写代码像是一行一行砌墙。Vibe Coding 更像是在和一个很快的搭档对话：

1. 先描述想要的效果。
2. 让 AI 给出第一版实现。
3. 运行、观察、指出哪里不对。
4. 继续收窄需求，直到结果可用。

这个过程的重点不是“提示词有多神”，而是反馈循环足够短。只要能快速看到结果，就能快速修正方向。

## 一个可用流程

先写清楚目标：

> 我想做什么？用户看到什么？输入是什么？输出是什么？什么情况算完成？

再让 AI 生成最小版本。不要一开始就要求架构完美，先让它跑起来。

接着自己运行和检查。看到报错就把完整报错给 AI，看到体验问题就描述具体画面和预期。不要只说“不好用”，要说“按钮太靠下”“移动端文字重叠”“保存后没有提示”。

最后做收尾：

- 删除没用的代码。
- 统一命名和格式。
- 补上关键测试。
- 自己读一遍核心逻辑。
- 确认没有把密钥、隐私数据或临时代码提交进去。

## 提示词写法

有效的提示词通常包含四件事：

- 背景：现在项目是什么，相关文件在哪里。
- 目标：要实现什么结果。
- 约束：不能改什么，必须保持什么风格。
- 验收：怎样判断完成。

示例：

```text
在现有 MkDocs 笔记站里新增一篇中文笔记。
文件放在 docs/，并把它加入 mkdocs.yml 的 nav。
保持当前站点风格，不要改主题配置。
完成后运行 mkdocs build 验证。
```

越具体，AI 越像工具；越模糊，AI 越像在猜。

## 需要保留人的判断

Vibe Coding 最容易出问题的地方，是把“生成得很快”误认为“结果是对的”。

AI 可能会写出能运行但不合理的代码，也可能会编出不存在的 API，还可能在修 bug 时顺手改坏别的地方。所以人必须保留几个动作：

- 读关键路径代码。
- 跑测试或手动验证核心流程。
- 看 git diff，确认修改范围符合预期。
- 对安全、数据、权限、支付等高风险位置保持谨慎。

## 我的使用原则

我更愿意把 Vibe Coding 当成“加速器”，不是“自动驾驶”。

它可以帮我跨过空白页，可以把想法变成第一版，可以替我做重复劳动。但最终我仍然要知道这个东西为什么能跑、哪里可能坏、以后怎么维护。

最舒服的状态是：我不再被语法和样板代码拖住，但仍然掌握方向盘。
